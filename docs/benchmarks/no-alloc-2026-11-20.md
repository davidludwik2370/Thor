# Allocation-contract cost, 2026-11-20

Measured on macOS 15.6, arm64, using release Rust compilers. The saved compiler
from before this feature is compared with the final compiler, first without
contracts and then with `#+vet no_alloc` on the same program. Compiler binary
hashes, every wall time, stage profiles, and emitted-source hashes are in the
[raw results](no-alloc-2026-11-20.json).

## Results

Median process wall time, including compiler startup, in milliseconds:

| Transpile workload | Before feature | Current, no contract | Current, contract enabled |
| --- | ---: | ---: | ---: |
| Small scalar program | 33.35 | 34.17 | 33.50 |
| 1,002-procedure shared call graph | 127.98 | 126.86 | 151.45 |
| SDK scalar math, aliased callback | 33.75 | 32.83 | 55.58 |

| Full optimized build | Before feature | Current, no contract | Current, contract enabled |
| --- | ---: | ---: | ---: |
| Small scalar program | 212.22 | 214.07 | 213.45 |
| Shared call graph | 377.82 | 383.06 | 403.57 |
| SDK scalar math | 219.77 | 214.45 | 239.27 |

Without a contract, the allocation-analysis stage and its procedure visits are
absent. The before/after sample ranges overlap in each workload; these results
show no significant normal-build slowdown. They do not claim that a handful of
runs can establish a universal sub-millisecond bound.

With contracts, the median allocation-analysis stage itself took **0.10 ms** for
the small program, **32.34 ms** for the call graph, and **17.18 ms** for SDK math,
including demanded SDK discovery. Whole-transpile differences were approximately
25 ms for the graph and 23 ms for SDK math. Stage and total-time differences need
not match exactly: reused type facts can reduce subsequent work, and process and
filesystem timing vary.

The graph verifies its 1,002 reachable procedures once each, including the leaf
shared by 1,000 callers. The SDK case inspects three procedures. This checks
sharing rather than measuring only an isolated leaf annotation.

## Runtime and methodology

**All three variants emitted identical Odin code in every workload**, after
removing blank lines introduced by stripping the file policy. The checker adds
no runtime instrumentation, allocator interception, ABI changes, or new
optimization decisions. Separate checked/unchecked/debug runtime tests verify
correct results and zero tracked allocations; see the
[validation report](../no-alloc-validation-2026-11-20.md).

There are 11 paired transpile measurements and three paired optimized builds
per variant, with warmed shared parser/evaluation caches and isolated generated
output directories. Variant order alternates each iteration. Only the file-policy
marker changes between enabled and disabled runs, with source offsets preserved
by whitespace padding. Measurements ran without concurrent build/test jobs.

Reproduce using a saved pre-feature release compiler:

```sh
python3 tools/benchmark_no_alloc.py \
  --baseline /path/to/pre-feature/thor-rust \
  --runs 11 --build-runs 3 \
  --output /tmp/no-alloc-results.json
```

These are warm compiler-process measurements, not cold-machine timings or an
application throughput benchmark. The unchanged emitted code is the stronger
evidence that verification itself introduces no runtime cost.
