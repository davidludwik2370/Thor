# Thor source debugging

Thor uses the installed CodeLLDB extension and an unmodified Odin compiler.
The Thor extension contributes a `thor-lldb` adapter and breakpoint support for
the `thor` language, independently of TLS's editing features.

## Start a project

Run `thor new my_project` to create `./my_project`, or `mkthor my_project` to
create `~/Code/Thor/my_project` and open VS Code. Only three files are created:

- `my_project.thor`: copied from the installation's editable `templates/main.thor`.
- `.vscode/tasks.json`: normal run and `-debug -o:none` build process tasks.
- `.vscode/launch.json`: the `thor-lldb` executable and matching manifest paths.

`thor new --open` opens VS Code; `mkthor --no-open` suppresses opening.
`--parent path` changes the parent directory, `--template path.thor` chooses
another starter, and `--gitignore` adds optional build/cache ignore rules.
Existing folders and symlinks are rejected. TLS discovers the shared installation
without a local settings file. Tasks record this installation's Thor path;
update that path if you relocate it or use another computer. Names ending in
platform, architecture or test suffixes retain Odin's filename selection rules;
the creator warns about these names and preserves the requested source filename.

Install the local Thor VSIX and CodeLLDB, open the generated Thor file, set a
breakpoint and press **Cmd+Shift+R**, or **F5**. The Thor extension's
**Thor: Debug Project** command supplies the shortcut. It saves files and selects
the folder's first `thor-lldb` launch configuration. The shortcut applies to Thor
editors while a debug session is not already active. Standard debug toolbar
buttons and existing VS Code stepping shortcuts continue to work.

**Cmd+R** runs **Thor: Run Project** without the debugger. It saves edits and
executes the folder's `run-thor` task in the integrated terminal. The task uses
`thor run .`, so sibling source files participate and stdin works normally.
Existing projects without a run task get a process task using the discovered
or configured compiler. A saved standalone `.thor` file without a workspace
folder runs in file mode. Non-macOS shortcuts are Ctrl+R and Ctrl+Shift+R.
Keyboard shortcuts are contributed by the extension, not a workspace
`keybindings.json` file.

## Existing projects

Add a build task using `thor build <package> -debug -o:none`, with an explicit
`--output-dir` and `-out:...`. Then use a launch configuration like this:

```json
{
  "name": "Debug Thor (LLDB)",
  "type": "thor-lldb",
  "request": "launch",
  "program": "${workspaceFolder}/.vscode/bin/debug",
  "manifest": "${workspaceFolder}/.vscode/bin/generated/thor-manifest.json",
  "cwd": "${workspaceFolder}",
  "args": [],
  "preLaunchTask": "build-thor-debug"
}
```

The task must build that executable and manifest together. Use the configuration
generated by `mkthor` as a complete example. Windows executables use `.exe`.
Optional launch properties include `stopOnEntry`, `terminal`, `env`,
`initCommands` and CodeLLDB's `expressions` setting. The bridge honors an explicit
`lldb.library` setting; otherwise it uses CodeLLDB's bundled LLDB library.

Reinstall the VSIX and reload the window after extension updates. Rebuilding TLS
or restarting the language server alone does not update the debug adapter.

Native macOS debug executable builds now also enable allocation tracking and
AddressSanitizer. Their runtime reports use original Thor locations, including
when the executable is launched directly. Other platforms retain ordinary debug
builds and source-mapped breakpoints without these automatic memory checks.
Use `--track-allocations=off` and/or `--no-sanitize` in the build task to disable
the macOS defaults. See [memory debugging](../../docs/memory-debugging.md).

## Why an adapter bridge

The prototype verified native breakpoint resolution, selected switch arms,
Step Over/Into/Out, pure-function wrappers, locals and imported Odin files using
ordinary Odin. A real VS Code test also steps into a user `fn` through an fstring
in a newly created project. This supports retaining the bridge rather than
maintaining an Odin fork or rewriting binary debug information.

```text
VS Code -- DAP --> Thor debug adapter -- DAP --> CodeLLDB / LLDB --> executable
                        |
                        +-- generated Odin maps --> original Thor locations
```

The adapter is implemented in `debug-adapter.js`; `debug-extension.js` registers
it with VS Code. Native execution, symbols, memory, threads and values remain
CodeLLDB's responsibility. Its adapter process is connected over an authenticated
loopback stream. Native debug information continues to refer to generated Odin;
the original-source experience is provided by the Thor adapter.
The TLS client's file watcher excludes generated debug/build output, including
custom output directories identified by their manifest, while watching original
source files normally.

Each build manifest includes a debug-map version and debug-library roots. Each
source-map sidecar retains original source snapshots, byte mappings and helper/
capture regions. The original diagnostic map format stays version 1; the new
region data is additive. The debugger requires matching maps from Thor 0.10+ and
a `-debug` build, and rejects sources edited since that build.
Generated-source and executable checksums also prevent combining maps with
edited generated files or a different binary. A failed build or a check-only
invocation cannot certify an old executable as matching new maps. Restart uses
VS Code's stop/build/start workflow so breakpoint locations are rebound to the
fresh build.

Breakpoint translation excludes generated type queries and closure capture
arguments: these can contain copies of an arm's source text before that arm runs.
It also rejects locations LLDB moves onto a different original statement.
Compiler-generated helpers are collapsed into their owning user stack frame;
locals can be retrieved from both the helper and its caller. Watch evaluation
falls back to the caller's scope when a captured name is absent from the helper.
Breakpoint conditions translate captured names to their native references.

Source stepping skips internal helper lines and standard-library housekeeping,
and avoids stopping again at the caller solely because a helper returned there.
Real breakpoint/exception stops are retained. Instruction stepping remains native.
Original editor path spellings, including symlinks, are retained for displayed
locations. Set values use their native Odin debug representation; custom Set
visualizers are a separate presentation refinement.

## Compile-time behavior and boundaries

`-debug` keeps optional runtime `fn` calls available for stepping, including calls
with literal arguments. `::` constants, array lengths, type/signature expressions,
generic constant arguments and explicit `#run` still evaluate at compile time.
There is no runtime execution of their compile-time helper to break into.
Non-debug builds retain normal automatic evaluation.

Watch, condition and debug-console expressions use CodeLLDB's evaluator, with
captured-name adaptation where needed. Arbitrary Thor syntax such as a new
fstring or Set operation is not interpreted in the Watch panel. Advanced mapped
step targets, hardware data breakpoints, jump-to-location and restart-frame
requests are disabled. Native
panic output outside the memory tracker and debugging directly with the `lldb` CLI still show native Odin
locations. Use the `thor-lldb` configuration for Thor source mapping.

## Validation

```sh
python3 -m unittest tests.test_mkthor tests.test_debugger -v
python3 tools/test_vscode_debug.py
cd editors/vscode
npm test
npm run package
```

The native tests use real CodeLLDB and Odin. Set `THOR_CODELLDB` to the installed
CodeLLDB extension directory if it is outside the default VS Code extensions
directory. The VS Code integration uses an isolated profile, a temporary mkthor
project and the installed CodeLLDB extension; `--codelldb` selects that directory.
It exercises the shortcut's command, pre-launch task, launch configuration,
breakpoint, stepping, watch/locals and clean termination. macOS is the end-to-end
validated platform for this local setup.
